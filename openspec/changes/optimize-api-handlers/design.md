# Design

## Context

See proposal.md — Why. FastEndpoints on ASP.NET Core 10; `PlannerDbContext` pooled, global profile filters; catalog served from the in-memory `IGameCatalogProvider.Current` snapshot whose `DatasetHashes[key]` is already in every dataset envelope. The manifest endpoint already implements the ETag/304 pattern via `ETagHelper`; this design reuses it.

## Goals / Non-Goals

**Goals:**
- Goal mutations ≤ 5 DB round trips after the pre-processor (today 10–13); list goals ≤ 2.
- Catalog first visit ≥ 70 % fewer bytes; repeat dataset fetch = 304.
- Upstream call volume bounded per profile.

**Non-Goals:**
- Any contract shape change, route rename, pagination, error-shape unification, schema change — all in `rebuild-foundation-pre-launch`.
- Output caching of per-user endpoints; distributed cache.

## Decisions

1. **Dataset ETag covers the complete representation.** Compute a strong validator from the bytes of the complete encoded representation of the full envelope (`Version`, `SchemaVersion`, `GameVersion`, `SourceHash`, `DatasetKey`, `DatasetHash`, and `Data`) using its negotiated content encoding; use `ETagHelper` to quote the resulting digest. Distinct identity/Brotli/gzip representations must have distinct strong validators and responses vary on `Accept-Encoding`. Cache the digest per immutable catalog snapshot/dataset/encoding rather than hashing on every request. Build the envelope and validator from the same captured snapshot. A metadata-only release change invalidates the validator even when `DatasetHash` is unchanged; the manifest's dataset hash continues to describe data, not the complete HTTP envelope. Use `Cache-Control: public, max-age=0, must-revalidate`; the manifest stays `private`. Hash-addressed immutable URLs remain deferred to the rebuild change.
2. **Compression via `AddResponseCompression` (Brotli, then gzip) with `EnableForHttps = true`** in `ServiceDefaults` so AppHost and container share it. BREACH is not a concern: responses carry no attacker-controlled reflected secrets (API keys are never returned; see `SecretMasker`).
3. **Two fixed-window rate-limit policies with separate endpoint buckets.** Implemented as a small `UpstreamRateLimiter` plus a global FastEndpoints pre-processor registered right after `CurrentUserPreProcessor`, not as `Microsoft.AspNetCore.RateLimiting` middleware: the middleware runs before identity resolution so it cannot key on the profile id without a synchronous DB lookup, its fixed-window limiter reports the full window rather than the time to the rejecting window's end, and it cannot take a `TimeProvider` for boundary tests. Endpoints opt in with `UpstreamRateLimit.Fast`/`Slow` endpoint metadata. `upstream-fast` (10/minute) applies to `POST tacticus-api-key/validate` and `PUT me/tacticus-integration`, and `upstream-slow` to `POST tacticus-integration/player-sync`, `POST guilds/register`, `POST guilds/me/sync`, and `POST me/v1-import` (6/hour). The partition key is `(profileId, HTTP method, canonical endpoint)`; before profile provisioning, use `(issuer, subject)` for identity. Policy names share configuration defaults, not quota: exhausting one endpoint does not consume another endpoint's bucket. Each bucket has non-overlapping windows of W seconds anchored at its first accepted request, no carry-over and no queue; permits renew at `t0 + kW`. Reject before any upstream call, persistence, or analytics. `Retry-After` is integer delay-seconds `max(1, ceil((windowEndUtc - nowUtc).TotalSeconds))` for the rejecting window; at the boundary a renewed window is evaluated before rejecting. Limits are configurable via the two existing planned keys.
4. **Snapshot projection for validation:** project `Characters.FirstOrDefault(u => u.UnitId == id)` / `Mows.FirstOrDefault(...)` from the snapshot — EF Core 10 + Npgsql translate `FirstOrDefault` over an owned JSON collection to `jsonb` path operators. If translation fails for the nested `Abilities`/`EquippedItems`, fall back to projecting the two chunk columns only (still skips the other nine). `CreateCombinedGoals` resolves the roster once and passes units into `ValidateAsync` (new overload taking the resolved unit).
5. **`GoalOrderService.CompleteAsync`:** take the already-tracked profile from the caller's unit of work (no `FirstAsync` + `ReloadAsync`), project only `(Id, GlobalPriority, Status)` for the density check, and load full goal rows only when renumbering is needed. The deferrable unique constraint is unchanged.
6. **Guild sync:** `profiles.Where(p => hashes.Contains(p.TacticusUserIdHash))` replaces the all-profiles load. **Raid status:** preserve the projector's complete inputs: load the latest boss observation and latest defeated-boss observation needed to derive position/cutoff, then select the latest observation after that cutoff for every relevant boss/side-boss encounter in the current position. Include the encounter's tier/set/index/type/progression identity when grouping, and use `(CompletedAt DESC, Id DESC)` for deterministic ties. Do not globally cap attack rows: one busy encounter must never hide another encounter's latest observation. Keep `GuildRaidStatusProjector` pure and verify equivalence with the full retained season, including side-boss modifier state and advancement after a kill.
7. **Player sync:** project `ChunkHashes`, `Revision`, and metadata before fetching upstream player data, so a slower response cannot adopt a newer revision after another request commits; write only changed JSON chunks plus metadata with a raw `UPDATE` (not `ExecuteUpdateAsync`, see Risks) using `WHERE profile_id = @profile AND revision = @projectedRevision`, and increment `Revision` atomically. Require exactly one affected row. Zero rows raises the existing optimistic-concurrency failure (HTTP 409 through the current handler); it must not silently retry a stale incoming payload over the winner. Snapshot updates, run/roster recording, and successful-sync metadata commit in the same production execution-strategy transaction; roll everything back on conflict. Both direct sync and V1 import use this same service path. For concurrent first inserts, roll back the loser; reuse the winner only if the transformed content is identical, otherwise return the existing concurrency failure instead of replaying stale input over the new row. Client single-flight, rate limits, and `configHash` are not concurrency guarantees; chunk hashes remain authoritative even when `configHash` is unchanged.
8. **Command-count assertions:** complete `replace-inmemory-api-tests-with-postgres` before implementation. Use `tests/TacticusPlanner.Api.IntegrationTests/PlannerApiFactory.cs` and its existing `CommandsFor(response)` helper against migrated PostgreSQL, retaining production pooling and the execution strategy. Count sync/async reader, scalar, and nonquery execution attempts once per attempt, including retries, pre-processors, and handlers; exclude migration/seed/assertion SQL outside the request and transaction begin/commit. The test-only response header exposes `HttpContext.TraceIdentifier`, isolating simultaneous requests. Baselines and endpoint ceilings for `POST me/goals/combined`, `POST me/goals/{id}/status`, `PUT me/goals/order`, and `GET me/goals` remain this change's regression gate. Preserve the targets above; record before/after using the same whole-request convention and identify pre-processor commands separately when assessing the mutation target.


## Risks / Trade-offs

- [EF Core JSON-collection `FirstOrDefault` translation varies by provider version] → spike first (one test against Testcontainers Postgres); the documented fallback keeps the win.
- [Rate limits too tight for V1-import retries] → `Retry-After` is honoured by the client and limits are configuration keys (`RateLimiting:*`), documented in README's settings table.
- [`ExecuteUpdateAsync` bypasses the `Revision` concurrency token] → guard every update by the projected revision, check the affected-row count, and roll back the whole sync unit of work on conflict; test racing direct sync and V1 import with unchanged `configHash` and different chunk content.

- [Decision 7 mechanism, resolved] Spike (EF Core 10 + Npgsql): `ExecuteUpdateAsync(set => set.SetProperty(s => s.Characters, ...))` throws `InvalidOperationException` ("The LINQ expression ... could not be translated") because the chunk columns are `OwnsMany(...).ToJson()` owned types, and a metadata-only tracked stub with a revision predicate makes `SaveChanges` rewrite every sibling JSON collection column as `[]`. Resolution: write changed chunks with a parameterized raw `UPDATE ... WHERE id = @id AND revision = @revision` (jsonb parameters from System.Text.Json, enums as numbers), guarded by `PlayerSnapshotJsonRoundTripPostgresTests`, which populates every chunk property by reflection and requires EF-written and directly-written rows to read back identically. Risk: a future chunk property with a custom EF value converter that System.Text.Json serializes differently would be caught by that test, not at runtime.

## Migration Plan

No migration. Deploy as a normal API release; rollback = previous image. Configuration keys for rate limits are optional with defaults.
